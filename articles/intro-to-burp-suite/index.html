An Intro To Burp Suite for Frontend Engineers

A required attribute, a disabled button, and a maxLength on an input are all polite suggestions. They shape what a cooperative user can do in the browser and say nothing about what the server will accept. The Network panel in DevTools shows you the request the form actually made. It won't show you the request the form refused to make, or the page the UI would have built if the JSON had said something else.

Burp Suite is how I look at that gap. It's an intercepting proxy from PortSwigger, and the free Community Edition covers everything in this article: installing it, scoping it to your app, reading traffic in HTTP history, and holding requests and responses so you can change them before they arrive. I've used it to push a form value past its maxLength and to flip a flag in an API response until a hidden button appeared. Both tests take a few minutes once Burp is set up, and I'll walk through each one.

This article is written against Burp Suite 2026.11.2, released November 18, 2026. Menu labels move between releases, so check them against your build.

What Burp gives you beyond DevTools

Burp sits between the browser and the server. Every request and response passes through it, so Burp can control an exchange while it travels, including stopping it before either side receives it.

DevTools can do some of this. You can edit and resend a request from the Network panel, and local overrides let you replace a response. The difference is where the control sits. DevTools works inside the browser, one tab at a time. Burp works on the connection between the browser and the server, and it keeps its own history of that traffic whether or not a tab stays open.

That position is what makes Burp useful to a frontend engineer. It gives you a way to investigate whether the API enforces the rules your frontend applies.

Install Burp and open its browser

Download Burp Suite Community Edition from PortSwigger. It's free and supports every exercise here. Run the installer and launch Burp. When it asks you to select a project file and configuration, click Next and then Start Burp to accept the defaults.

Burp comes with its own browser. Open it from Proxy > Intercept > Open browser. It's preconfigured to send its traffic through Burp and to trust Burp's certificate, so there's nothing else to install, even for HTTPS sites.

You also need something to point it at. Your own app, running locally or in a dev environment, is the best target because you know what it's supposed to do. If you'd rather practice on something built for it, PortSwigger's Web Security Academy has free labs, and Burp has an Academy tab for opening them directly.

Set your testing scope

Only test what you're authorized to test: your own applications, systems you have written permission to test, and practice labs. Running Burp against an app you build is ordinary development work. Before going further, confirm the system in front of you is one you're allowed to test, and stay in a non-production environment until you know your way around Burp's settings.

Scope in Burp involves three separate things, and setting one doesn't set the others.

Define it. Add your host to the target scope. The quickest way is to browse your app once, open Target > Site map, right-click your host, and choose Add to scope. You can also manage the list under Target > Scope. This records the target that other settings refer to.

Filter with it. When you add a host to scope, Burp can ask whether to stop logging out-of-scope items. Saying yes keeps analytics, fonts, and other third-party traffic out of your history from then on. For what's already there, open the filter settings above Proxy > HTTP history and select Show only in-scope items.

Enforce it. Defining and filtering don't stop the browser's requests to other hosts from going out. To do that, open Burp's Scope settings (Settings > Project > Scope), find Out-of-scope request handling, select Drop all out-of-scope requests, and choose Use suite scope. With that setting on, Burp drops out-of-scope outgoing requests even when the browser explicitly asks for them. You can also add a request interception rule in the Proxy settings that matches on your domain name, so Intercept only holds requests for your app.

If your page loads scripts, fonts, or API responses from other hosts, add those hosts to scope too, or the page may not load completely with enforcement on. Scope limits where requests go. Inside that boundary a delete is still a delete, so scope doesn't replace permission or a safe test environment.

Find a request in HTTP history

I'll use two exchanges as running examples. The endpoints and fields below are generic stand-ins, so substitute whatever your app actually calls.

The first is a form submit. A profile form has a display name input with a maxLength, and saving it sends a POST. With Intercept off, submit the form in Burp's browser, then go to Proxy > HTTP history and select the request. Clicking the # column header until it sorts descending puts the newest traffic at the top. The request and response appear together. The snippets in this article are simplified versions of what Burp's message editor shows, trimmed to the lines that matter, and they aren't meant as literal wire format.

POST /api/profile HTTP/2
Host: app.example.test
Content-Type: application/json
Cookie: session=...

{"displayName":"Emily"}

Read the method and the endpoint first, then the Content-Type header and the body, then the response status and whichever response fields matter to you. Also check whether a cookie or an Authorization header goes along with the request. That's how the server knows who you are, and it matters for anything you test later.

The second exchange is a GET the page makes when it loads. Its response includes a presentation flag that decides whether an Export button renders.

GET /api/account HTTP/2
Host: app.example.test

HTTP/2 200 OK
Content-Type: application/json

{"name":"Emily","showExportButton":false}

The Network panel would show you the same details. What Burp adds is a history that doesn't depend on any browser tab, and a direct path from looking at a message to holding the next one like it.

History keeps collecting while Intercept is off. PortSwigger's documentation says HTTP history is always updated, even when Intercept is off, so you can browse normally and review everything afterward. Once I'm past a single request, I keep Intercept off and turn it on only for the exchange I want to hold. If you want a particular state at startup, Burp has a user setting called Default Proxy interception state.

If you leave Intercept on, the browser will look like it's hanging. Burp is holding a message. Open Proxy > Intercept, Forward or Drop what's waiting, and click the toggle so it reads Intercept off.

Intercept and modify traffic

Changing a request

Turn Intercept on and submit the profile form with an ordinary value. Burp holds the request in Proxy > Intercept, where you can read it, edit it, Forward it, or Drop it.

In the message editor, replace the displayName value with one longer than the input's maxLength. If the input has maxLength="40", anything over 40 characters will do.

{"displayName":"A display name that runs well past the forty-character limit"}

Then click Forward. The browser enforced that limit while you typed, and it has no say over the request once the request has left the page. The attribute isn't necessarily the app's only check, either: its JavaScript may validate the field before submitting, and the server may apply rules of its own.

When I ran this, the edited request reached the server with the longer value, past the limit the browser had applied.

Then look at what happened next. Check the response status and body, check what the page shows, and reload to see what was stored. Write down whether the server rejected the value, cut it short, or saved all of it.

If a limit matters, the server has to enforce it, because anything that edits the request after it leaves the page can send a longer value. An accepted overlong value still doesn't prove the server is missing validation, since the API may intentionally allow longer values than the form does. Find the intended constraint first, from the API documentation, the schema, or the team that owns the endpoint, before calling anything a bug.

Changing a response

Now the GET. Loading a page fires a lot of requests: the document itself, scripts, stylesheets, images, and often several other API calls. With Intercept on, Burp holds each one in turn, so the first job is finding the right request.

  1. With Intercept on, reload the page in Burp's browser.

  2. Read the request line at the top of the held message. If it isn't GET /api/account, click Forward and check the next one. Keep forwarding unrelated requests until the account request is the one Burp is holding.

  3. Right-click that request and choose Do intercept > Response to this request.

  4. Click Forward. The request goes to the server, and Burp holds its response when it comes back.

  5. In the held response, change showExportButton from false to true, then click Forward.

The order of steps 3 and 4 matters. Response interception has to be set up before the matching response passes through the proxy, so choose Do intercept while the request is still held. If you forward first, the response goes straight to the browser, and you'll need to reload and start again.

An optional tip if the held requests are mostly noise: right-click one you don't care about and choose Don't intercept requests. This adds an interception rule that forwards matching messages automatically, such as everything from the same host or with the same file extension. If requests from that host stop being held later, check the interception rules in the Proxy settings.

In my test, the hidden Export button appeared on the page.

The frontend renders from the fields it receives, so a changed field produced a changed page. A rendered button grants no permission to use the endpoint behind it. The server has to check whether this account is allowed to export every time that request arrives, whatever the UI decided to show. Whether it actually does is a separate test of the protected operation, against a system you're authorized to test, and it belongs in a later article.

Editing a response is useful for ordinary frontend testing too. It lets you see how your UI handles server states that are hard to reproduce on demand, like a feature that's turned off, a value that's missing or unexpected, or an empty list, without waiting on the backend to produce them.

When you finish, Forward or Drop every held message and turn Intercept off. PortSwigger's Modifying HTTP requests with Burp Proxy tutorial covers the same request-editing workflow against a practice lab if you want a second pass.

How HTTPS interception works

Most apps run over HTTPS, so Burp has to decrypt traffic to show it to you. It does that by presenting its own certificate for each site you visit. Burp creates a unique certificate authority (CA) for your installation, stores it on your computer, and uses it to sign a certificate for each host. A browser accepts those certificates only if it trusts Burp's CA.

Burp's browser already trusts it, which is why the install step didn't need a certificate. You may notice HTTPS struck through in that browser's address bar. PortSwigger documents this as a TLS alert that appears because the browser can tell it isn't talking directly to the real server. In Burp's browser, that's expected.

Installing Burp's CA in any other browser has consequences. Anyone who has the CA's private key could intercept TLS traffic in that browser without an obvious warning, even when Burp isn't running. PortSwigger advises against installing it if untrusted people can read local data on your computer. If you do install it, treat it as temporary and remove it when the work is done.

Optional: use an external browser

If you'd rather test in a browser you already use:

  • Point the browser's proxy settings at Burp's listener, which defaults to 127.0.0.1:8080.

  • With the proxy set, visit http://burpsuite to download Burp's CA certificate, then install it as a trusted root in that browser.

  • Remove the certificate when you finish.

PortSwigger's external browser configuration pages have browser-specific steps. Follow those rather than guessing at menus, since they change with every browser release.

What to know before closing Burp

Community Edition uses a temporary project. Your history, scope, and everything else in it are gone when you close Burp, so save or copy out anything you want to keep first. Burp Suite Professional can save project files to disk.

Anything you do keep deserves care. Saved requests, exports, and screenshots can contain cookies, tokens, and personal information. Redact them before you share them, and delete exports you no longer need.

If you installed Burp's CA in another browser, remove it now.

CSS Anchor Positioning Is Ready for Your Tooltips

A tooltip should be the smallest thing on the page, and for years it has carried a positioning library, resize and scroll listeners, and a standing z-index dispute with every modal in the app. I’ve written that hook on top of Popper more times than I care to count, sometimes with focus traps, scroll locks, and tooltips bundled into one reusable pile of measurement code. Every version still used JavaScript to answer a question that belongs to CSS: where should this box sit relative to that one?

CSS anchor positioning hands that calculation to the browser. You name an anchor, associate another element with it, and provide alternate placements for when the first one doesn’t fit. Add the Popover API and you can put a tooltip in the top layer, clear a clipping ancestor, and flip at the viewport edge without writing your own positioning math.

Firefox enabled anchor positioning by default in version 147 on January 13, 2026, including Firefox for Android. The newer Firefox ESR 153 line has it too, so waiting for Firefox is no longer a good reason to keep a positioning library. I’d use native anchor positioning as the default for a new design-system tooltip, with JavaScript for hover and focus behavior and a fallback for browsers that still need one.

How a tooltip finds its anchor

The trigger declares a name with anchor-name, and the tooltip refers to it with position-anchor. Anchor positioning applies to absolutely positioned boxes, so the tooltip needs position: absolute or position: fixed.

.trigger { anchor-name: --save; }

.tooltip {
  position: absolute;
  position-anchor: --save;
}

Anchor names are dashed identifiers, with the same -- prefix as CSS custom properties. If several elements share a name, the browser prefers a matching ancestor of the tooltip; otherwise it uses the last eligible match in DOM order. anchor-scope lets you restrict a name to a component’s subtree, which matters when the same markup appears in a list.

Placement uses a three-by-three grid around the anchor, with the anchor occupying the center. The position-area property places the tooltip in one of the surrounding cells or in an area spanning several of them. You describe where the tooltip belongs and the browser places it, so there are no coordinates to calculate with getBoundingClientRect().

The usual containing-block rules still apply. An absolutely positioned tooltip can be clipped by an overflow: hidden ancestor, and the anchor must be eligible for the browser to use it. I’ve worked around clipped tooltips and menus with React portals, which work but add another layer to debug. A popover is often the simpler answer: an open popover lives in the top layer, outside ordinary ancestor clipping. For an ordinary anchored tooltip, position: absolute is a useful starting point; choose fixed when you need viewport-relative positioning.

Placing the tooltip

A basic tooltip needs a placement and an alignment. This example sits above the Save button and centers on it.

<button class="trigger" aria-describedby="save-tip">Save</button>
<span class="tooltip" id="save-tip" role="tooltip">
  Saves a draft. Nothing is published.
</span>

.trigger { anchor-name: --save; }

.tooltip {
  position: absolute;
  position-anchor: --save;
  position-area: top;
  justify-self: anchor-center;
  margin-block-end: 0.5rem;
}

position-area: top places the tooltip above the button, and justify-self: anchor-center aligns their horizontal centers. Firefox shipped anchor-center alongside anchor positioning in version 147. The tooltip is always visible in this first example so you can check the placement before adding interaction.

When a help tip should line up with one edge of its label, span-* values such as top span-right or bottom span-left extend the placement area. For right-to-left layouts, use logical values such as inline-start and inline-end so the placement responds to writing direction.

There was a viewport-overflow bug with single physical position-area keywords in Firefox 147 and Chrome versions before 144. place-self: anchor-center was a workaround; Firefox 148 and Chrome 144 corrected the behavior. It matters if you’re testing older builds, but doesn’t need a workaround in current ones.

For a menu that must match its trigger’s width, or an arrow that needs a precise offset, anchor() and anchor-size() give you access to the anchor’s edges and dimensions.

.menu {
  position: absolute;
  position-anchor: --combobox;
  top: anchor(bottom);
  left: anchor(left);
  width: anchor-size(width);
}

anchor(bottom) uses the anchor’s bottom edge, and anchor-size(width) gives the menu the same width as its trigger. That width matching used to be a job for Floating UI’s size() middleware. You can use anchor-size(height) the same way. Watch out for left: anchor(center), which puts the menu’s left edge at the anchor’s midpoint and leaves the menu off-center. To center the menu on its trigger, use justify-self: anchor-center.

It’s possible to combine position-area with anchor() insets, but I’d keep one positioning approach per component unless a particular offset requires both. Otherwise the CSS becomes another set of calculations to maintain.

For entrance animations, I animate transform and opacity and leave the inset properties, anchor(), and anchor-size() alone. A small scale-and-fade animation with a suitable transform-origin works across browsers, and it should be disabled or reduced when prefers-reduced-motion is set.

Note: I suggest using transform because transform and opacity animations can run on the GPU, while animating an inset or a size forces layout on every frame and causes rendering issues. That approach also doesn’t work in Firefox, which can’t interpolate the anchor functions.

When the tooltip runs out of room

The placement above the trigger works until the trigger approaches the top of the viewport. CSS can try alternate positions in order.

.tooltip {
  position-area: top;
  position-try-fallbacks: flip-block, flip-inline;
  position-visibility: anchors-visible; /* Firefox */
  position-visibility: anchor-visible; /* Chrome 157+, Safari 27 */
}

@position-try --right-side {
  position-area: right;
  margin-inline-start: 0.5rem;
}

.tooltip.fancy {
  position-try-fallbacks: --right-side, flip-block;
}

flip-block tries the other side of the block axis when the original placement doesn’t fit; flip-inline does the same on the inline axis. For a placement the built-in fallbacks don’t cover, define an @position-try rule. A crowded toolbar might try the right side before moving the tooltip below. The browser takes the first position that fits. For taller content, position-try-order: most-height can favor the option with more available height.

The two position-visibility declarations account for a specification rename. Firefox currently uses anchors-visible, while Chrome 157 and Safari 27 support the singular anchor-visible; Chrome also retains the plural spelling as an alias. Browsers ignore declarations they don’t understand, so each can use the spelling it supports. Hiding a positioned element when its anchor leaves view is already the property’s initial behavior, but writing it here makes the intent explicit.

Putting the tooltip in the top layer

The Popover API solves the clipping problem without a React portal. An open popover is rendered in the top layer, above ordinary page content.

<button
  popovertarget="tip-1"
  aria-describedby="tip-1"
  aria-label="About autosave"
>?</button>
<div id="tip-1" popover="auto" role="tooltip">
  Drafts autosave every 30 seconds.
</div>

[popover][role="tooltip"] {
  margin: 0;
  inset: auto;
  position-area: top;
  position-try-fallbacks: flip-block;
}

A button with popovertarget implicitly anchors the popover it opens, so this example doesn’t need an anchor-name. That association works in Chrome 133+, Firefox 147+, and Safari 26+. The margin and inset declarations override the user-agent styles that would otherwise center the popover in the viewport.

This particular example opens on click, which makes it a toggletip. It demonstrates the positioning and top-layer behavior; the hover and focus interaction still needs to be added.

In repeated components, you can reuse the same anchor name without collisions by scoping it to each row.

.list-item {
  anchor-scope: --row;
  anchor-name: --row;
}

.list-item .tooltip {
  position: absolute;
  position-anchor: --row;
  position-area: right;
}

anchor-scope is available in Chrome 131+, Firefox 147+, and Safari 26+.

Hover, focus, and popover behavior

Anchor positioning determines where the tooltip goes; it doesn’t decide when to open it. The interestfor attribute can handle interest-based interactions declaratively, but in November 2026 it remains Chromium-only, starting with Chrome 142. I wouldn’t make a design system’s basic hover behavior depend on it while Firefox and Safari lack support.

For a tooltip that isn’t a popover, :hover and :focus-visible can control visibility. For a popover, use showPopover() and hidePopover() in pointer and focus handlers. A small amount of JavaScript is still reasonable here, particularly when you need a delay before opening or closing. That JavaScript no longer has to measure the trigger or calculate the tooltip’s position.

popover="hint" is a better interaction model when browser support allows it. A hint can appear while an existing auto popover, such as a menu, stays open, where opening an unrelated auto popover would close the menu. It supports Escape and light dismiss as well. Chrome 151+ and Firefox 153+ support the current behavior; Safari added it in the 27.3 beta. Clicking an invoker outside an open auto popover still light-dismisses that auto popover, even if the invoker opens a hint. For now, detect hint support or use auto with that interaction tradeoff in mind.

Accessibility

A tooltip provides supplementary information. Associate it with its trigger using aria-describedby, and put information needed to complete a task directly into the visible interface. popovertarget controls the opening behavior, but it doesn’t create an accessible description. That’s why the popover example includes both attributes.

The tooltip also needs to work with the keyboard. WCAG 2.2 success criterion 1.4.13, Content on Hover or Focus, requires additional content to be dismissible, hoverable, and persistent under the conditions the criterion describes. Escape is the customary dismissal key, and auto and hint popovers handle it for you. A manually controlled tooltip needs its own dismissal behavior.

Hoverability is easy to break without noticing. The gap introduced by a tooltip’s margin also becomes a gap the pointer has to cross. If your code hides the tooltip as soon as the pointer leaves the trigger, someone may never reach the tooltip itself. Keep it open while the pointer is over either the trigger or the tooltip, and make sure the handoff between them works in both directions. Test keyboard focus, too; anchoring and the top layer don’t provide interaction behavior for you.

Browser support as of November 17, 2026

Anchor positioning has been enabled by default in Firefox since version 147. Mozilla shipped it on January 13, 2026, after versions 145 and 146 kept it behind the layout.css.anchor-positioning.enabled flag. The main positioning features now work in current Chrome, Firefox, and Safari, although some newer values still differ by engine.

Can I Use still marks Firefox as having partial support, notably because it doesn’t interpolate anchor() or anchor-size() and hasn’t shipped the new singular position-visibility values in its stable release. Those gaps needn’t block the tooltip shown here: its entrance can animate with transform and opacity, and Firefox accepts the older anchors-visible spelling. Can I Use also still lists Chrome as partial, despite Chrome 157 supporting the renamed values. Can I Use reported roughly 88% global support when full and partial support were counted together on November 16, 2026.

Check managed browser installations separately. Firefox ESR 153, released July 21, 2026, includes anchor positioning. ESR 140 went out of support on September 29, while ESR 115 remains on an extended maintenance path for older Windows and macOS systems through March 2027. A company can also pin a browser version beyond its ordinary support window. Check your audience before removing the fallback.

@supports not (anchor-name: --a) {
  .tooltip {
    /* Use a static placement, or keep a JavaScript positioning path. */
  }
}

A static fallback is enough if the tooltip can remain usable without matching the trigger’s exact geometry. If it can’t, retain Floating UI or consider OddBird’s anchor-positioning polyfill. My own migration used native anchor positioning with a small JavaScript polyfill. A polyfill cannot make CSS.supports() report native support. If you use one, keep the anchor-positioning rules outside any @supports block that fails in older browsers, so the polyfill can read them.

Migrating a design-system tooltip

If the current component uses Floating UI, much of its positioning configuration maps directly to CSS.

Floating UICSS anchor positioning
placement: 'top'position-area: top
flip()position-try-fallbacks: flip-block
size()anchor-size()
hide()position-visibility: anchor-visible (or anchors-visible in Firefox)

These map common jobs, and some middleware options have no direct CSS equivalent. JavaScript is still the right tool for virtual anchors such as cursor-following tips, complex arrow geometry, and hover delays that interestfor cannot yet handle across browsers. It no longer needs to calculate ordinary trigger-relative placement, flipping, or width matching.

I’d migrate in stages. Keep the component’s React API unchanged, introduce the CSS positioning path, and test it against your current hover, focus, and dismissal behavior. For an older-browser fallback, choose either a separate Floating UI branch or a polyfill, then test the path you’ve actually chosen. After a release with browser analytics, remove the old positioning code if the unsupported share is small enough for your product.

The first component I’d migrate is the ordinary tooltip attached to a button or label. If it works with a couple of positioning declarations and a popover, there’s little reason to keep a resize-and-scroll measurement loop around it.
